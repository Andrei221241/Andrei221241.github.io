1. Introduction

This week involved evaluating the server’s performance under various workloads to analyse operating system behaviour. Baseline system metrics were recorded and compared against results from CPU, memory, disk I/O, network throughput, and latency tests. Performance data was collected using command-line tools and used to identify system capacity, responsiveness, and potential bottlenecks. The results provide quantitative evidence of system stability and performance characteristics.

Optimisation analysis

  • Firewall restrictions (reduced attack surface and overhead): The server firewall was configured to allow only required inbound services and block everything else by default. This reduces unsolicited traffic (e.g., scans and random connection attempts), which in turn reduces wasted CPU cycles and unnecessary log writes. A quieter baseline helps ensure benchmark results (CPU, disk, and network tests) are not affected by unrelated background activity.
  • SSH key authentication (reduced authentication load): SSH access was hardened by using public key authentication instead of password-based logins. This reduces repeated password checking attempts and lowers the likelihood of brute-force activity, which also reduces CPU usage and log “noise” over time.
  • Fail2ban (prevents brute-force and reduces log/CPU churn): Fail2ban was enabled to detect repeated failed login attempts and temporarily ban offending IP addresses. This prevents sustained brute-force attempts from consuming resources and generating large volumes of authentication logs, keeping the VM more stable during long uptime periods.
  • No swap usage observed (memory sized appropriately): During testing, swap usage was not observed, indicating the VM has sufficient RAM for the workload. Avoiding swap activity reduces the risk of latency spikes and performance instability, especially under sustained load.

Together, these improvements reduce unnecessary background processing and improve security posture without requiring major system changes, supporting more consistent and reliable performance results.

8. Bottleneck Analysis

Combining results from CPU, disk and network tests leads to the following overall assessment of system bottlenecks:

  • CPU: The inability of stress-ng to produce metrics appears to stem from VirtualBox’s handling of performance counters and timing, not from the Ubuntu scheduler.
  • Memory: Baseline measurements showed more than 8 GiB of free RAM, and none of the tests produced evidence of swapping or memory pressure.
  • Disk I/O: The 2.1 GB/s figure on the server VM is likely an artefact of virtualised caching rather than genuine disk performance.
  • Network: Very high throughput combined with high retransmission rates indicates a bottleneck within the VirtualBox networking stack. Socket buffer tuning in the guest OS had no measurable effect.

9. Reflection

The experiments confirmed that while command-line tools such as stress-ng, dd, ping and iperf3 are powerful for understanding OS behaviour, their outputs must be interpreted in the context of the underlying platform. In a fully virtualised environment, the hypervisor can distort CPU metrics, cache disk writes aggressively and implement networking via virtual switches that behave differently from physical networks.

Apparent performance values may therefore reflect the efficiency of the virtualisation layer rather than the intrinsic performance of the Linux kernel or its configuration. The optimisation attempts around network buffers reinforced this point by showing that tuning within the guest OS cannot overcome limitations imposed by VirtualBox’s implementation.
