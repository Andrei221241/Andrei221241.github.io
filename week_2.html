Week 2: Security Planning and Testing Methodology

Objective

In Week 2, I planned the security baseline for the Ubuntu Server and outlined a performance testing methodology. This phase focuses on planning, not implementation.

1. Security Baseline Checklist

Security Area Planned Configuration / Notes
SSH Hardening Disable password authentication, enable key-based authentication, restrict SSH access to the workstation IP. Ensures only authorized users can log in remotely.
Firewall Configuration Configure ufw to allow only essential ports (SSH) and block all others. Protects server from unauthorized network access.
Mandatory Access Control (MAC) Use AppArmor to enforce process-level security policies. Limits the impact of compromised applications.
Automatic Updates Enable unattended security updates to ensure all security patches are applied promptly.
User Privilege Management Create a non-root administrative user; enforce sudo usage. Minimizes risk of accidental or malicious system changes.
Network Security Keep server on Host-Only network to isolate it from external networks. Plan to monitor for unauthorized access attempts.

Explanation: Each control is selected to reduce the risk of common security threats and to follow best practices for server hardening.

2. Threat Model

Threat Description Mitigation Strategy
Unauthorized SSH access Attackers may try to guess passwords or brute-force login attempts. Disable password login, enable key-based authentication, enforce IP restrictions, and use fail2ban (later).
Malware / compromised packages Malicious software could be installed on the server. Enable automatic security updates and verify software sources before installation.
Privilege escalation Non-admin users could gain root access. Proper user management, enforce sudo usage, and use AppArmor for access control enforcement.

Explanation: Identifying these threats ensures a proactive approach to securing the server before deployment.

3. Performance Testing Methodology

Although performance testing will be performed in Week 6, I planned the approach now:

Metric Measurement Method Notes
CPU Usage top, htop, or mpstat Measure baseline and load usage for different applications.
Memory Usage free -h, vmstat Monitor RAM and swap usage during workloads.
Disk I/O iostat, dd Record read/write speeds and identify potential bottlenecks.
Network Performance ping, iperf Measure latency and throughput for network-intensive applications.
System Latency / Responsiveness Observe delays under load Identify if applications cause slow system responses.

Explanation: Metrics will be collected via command-line tools and recorded systematically to evaluate the server’s behavior under different workloads.

4. Reflection

In Week 2, planning the security baseline and performance testing methodology helped me develop a deeper understanding of the potential vulnerabilities and risks associated with the Ubuntu Server. This planning ensured that all future server configurations, monitoring, and testing activities will be structured, consistent, and measurable. By carefully considering areas such as SSH hardening, firewall rules, access control, and automated updates, I was able to create a clear roadmap for Week 4 and beyond. Focusing on documentation and planning at this stage establishes a solid foundation for implementing security controls and evaluating performance systematically, which will ultimately support a more secure and efficient server environment.
