Introduction

Week 5 focused on implementing the advanced security and monitoring features needed to strengthen the Ubuntu Server configured earlier in the project. The aim was to protect the system against common threats while enabling reliable remote administration. All work was performed over SSH from the workstation, maintaining a headless-server management workflow.

Objectives

The objective for this week was to enhance the server’s security posture by enabling mandatory access control (AppArmor), configuring automatic security updates, deploying fail2ban to prevent unauthorized SSH access, and validating protections using a custom baseline script. Additionally, a remote monitoring script was created to collect system performance metrics securely over SSH.

1. Implement Access Control using AppArmor

For mandatory access control, I used AppArmor (the default on Ubuntu) to ensure that key services, including the SSH daemon, run under enforced profiles. This provides finer-grained control beyond traditional UNIX permissions.

Checking and enforcing AppArmor

sudo systemctl status apparmor          # Verify that the AppArmor service is running
sudo aa-status                          # List loaded profiles and their mode (enforce/complain)
sudo aa-enforce /etc/apparmor.d/usr.sbin.sshd  # Enforce the sshd profile if not already enforced

The aa-status output provides a simple way to track and report on access control settings, listing how many profiles are in enforce or complain mode and whether any processes are unconfined.

2. Configure Automatic Security Updates

To keep the server patched without manual intervention, I configured unattended security updates.

Installing and enabling unattended-upgrades

sudo apt install unattended-upgrades -y                 # Install unattended upgrades package
sudo dpkg-reconfigure --priority=low unattended-upgrades  # Enable and configure automatic updates
cat /etc/apt/apt.conf.d/20auto-upgrades                # Verify periodic update and upgrade settings

The 20auto-upgrades configuration file confirms that the server will regularly check for updates and automatically install security patches, with log entries written to /var/log/unattended-upgrades/ for auditing.

3. Configure fail2ban for Intrusion Detection

fail2ban was installed and configured to monitor SSH logins and temporarily ban IPs that exhibit brute-force behaviour.

Installing and enabling fail2ban

sudo apt install fail2ban -y     # Install fail2ban framework
sudo systemctl enable fail2ban   # Ensure fail2ban starts on boot
sudo systemctl start fail2ban    # Start the fail2ban service
sudo fail2ban-client status      # View overall fail2ban status and configured jails

Additional jail configuration for SSH was recorded in /etc/fail2ban/jail.local to define ban time, find time and max retries. The fail2ban-client command was used to report on active jails and current bans.

4. Security Baseline Verification Script (security-baseline.sh)

To verify that all controls from Phases 4 and 5 remain correctly configured, I created a security-baseline.sh script that runs on the server. It checks AppArmor, SSH configuration, UFW rules and fail2ban status. The script includes line-by-line comments to explain each step.

Script contents

#!/bin/bash
# security-baseline.sh
# Verifies security controls from Phases 4 and 5 on the Ubuntu Server.

echo "== Security Baseline Check =="

# 1) Check AppArmor is active and sshd profile enforced
echo "[*] Checking AppArmor status..."
aa-status | grep "profiles are in enforce mode"

# 2) Confirm SSH root login and password auth are disabled
echo "[*] Checking SSH hardening..."
grep -E "PermitRootLogin|PasswordAuthentication" /etc/ssh/sshd_config

# 3) Verify UFW is enabled and SSH restricted to workstation IP
echo "[*] Checking UFW firewall rules..."
ufw status

# 4) Check fail2ban service and SSH jail
echo "[*] Checking fail2ban service..."
systemctl is-active fail2ban
fail2ban-client status sshd

echo "== Baseline check complete =="

Executing the script remotely over SSH

chmod +x security-baseline.sh
ssh adminuser@192.168.56.10 'bash -s' < security-baseline.sh

Running the script via SSH from the workstation satisfies the “headless” and “remote only” administration constraints while providing a reproducible way to verify the full security baseline.

5. Remote Monitoring Script (monitor-server.sh)

To support ongoing monitoring, I created monitor-server.sh on the workstation. The script connects to the server via SSH, runs a set of diagnostic commands, and prints the results in one go. Again, it is fully commented line-by-line.

Script contents (workstation)

#!/bin/bash
# monitor-server.sh
# Runs basic monitoring commands on the Ubuntu Server via SSH.

SERVER_USER="adminuser"          # SSH user on the server
SERVER_HOST="192.168.56.10"      # Server IP address on host-only network

echo "== Remote Server Monitoring =="
echo "Target: ${SERVER_USER}@${SERVER_HOST}"
echo

# Run monitoring commands on the remote server in a single SSH session
ssh "${SERVER_USER}@${SERVER_HOST}" << 'EOF'
echo "[*] System information (uname -a)"
uname -a
echo

echo "[*] Memory usage (free -h)"
free -h
echo

echo "[*] Disk usage (df -h)"
df -h
echo

echo "[*] Network interfaces (ip addr)"
ip addr
echo
EOF

echo "== Monitoring run complete =="

Executing the monitoring script

chmod +x monitor-server.sh
./monitor-server.sh

Because the script itself runs on the workstation and connects via SSH, it fits the requirement that monitoring must be remote and does not require logging into the server console directly.

Reflection

This week pushed the server beyond basic hardening and into a more maintainable security model. AppArmor, unattended-upgrades and fail2ban each strengthened different layers of defence, but the real shift was seeing how they work together: access control restricting what services can do, automated patching reducing exposure, and intrusion detection reacting to hostile behaviour.

Building the two scripts clarified this even further. The security baseline script turned abstract “checks” into a repeatable verification process I can run any time the system changes. The monitoring script created a simple way to observe performance remotely without touching the server console. Together they made the setup feel more like a system that can be operated and trusted over time, not just configured once.
