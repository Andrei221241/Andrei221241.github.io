Phase 7: Security Audit and System Evaluation (Week 7)

This phase conducts a security audit of the deployed Ubuntu Server and evaluates the overall configuration, using command-line tooling only and remote administration via SSH.

Introduction

Week 7 concludes the operating systems project with a comprehensive security audit of the Ubuntu Server environment built throughout Weeks 1–6. This phase shifts focus from implementation to evaluation, requiring a methodical assessment of system security, configuration integrity and service behaviour. Using only command-line tools over SSH, I performed an end-to-end audit including Lynis scans, nmap external probing, AppArmor and SSH hardening verification, and a full service inventory. The goal was not only to confirm that the server remained functional but to demonstrate—through evidence—that it met the security, performance and configuration expectations defined earlier in the project. This week represents the transition from building a system to validating and defending it through structured reporting, mirroring professional security auditing practice.

1. Introduction

Week 7 concludes the operating systems project with a full security audit of the deployed Ubuntu Server. Following the assessment brief’s Phase 7 requirements, I performed a comprehensive evaluation using Lynis, nmap, access control validation, service review, and configuration checks. All tasks were executed remotely via SSH, maintaining the command-line–only administration constraint.

2. System Audit with Lynis

Lynis was used to perform a deep security scan of the server. This helped identify misconfigurations, opportunities for strengthening the system, and produced a security score.

Command Used

sudo lynis audit system

Before Remediation Score: Hardening index 59.

After Remediation Score: Hardening index 63.

3. Network Security Assessment (nmap)

An external security scan was performed from the workstation using nmap to verify the firewall and ensure only SSH was reachable.

Command Used

sudo nmap -sV -O 192.168.56.10

The scan confirmed that port 22 was the only open port, aligning with the firewall rules set in Weeks 4 and 5.

4. Access Control Verification

I reviewed AppArmor status, SSH daemon configuration, and privilege assignments to ensure that the principle of least privilege was respected. 

sudo aa-status | head -n 10
sudo cat /etc/ssh/sshd_config | grep -E "PermitRootLogin|PasswordAuthentication"
id adminuser

5. Service Inventory & Justification

Using systemctl --type=service --state=running and ps aux, I compiled a list of all active services and evaluated whether they were required for the system’s intended function.

Unnecessary or unused services were disabled to reduce the attack surface.

6. Overall System Evaluation & Remaining Risk

The combined security controls from Weeks 4–7 create a robust environment aligned with the coursework learning outcomes. The final audit confirms that:

  • The firewall allows only authorised traffic (SSH from the workstation).
  • SSH operates strictly with key-based authentication and no direct root access.
  • Access control (AppArmor) restricts system processes to defined profiles.
  • fail2ban and automatic updates strengthen long-term resilience and patching.
  • No unnecessary network-exposed services remain active.

Residual risk mainly relates to the limits of a single-host setup (no redundancy) and dependencies on VirtualBox networking. These are noted in the written report as design rather than configuration risks.

7. Reflection

Week 7 brought together all the work from previous weeks and shifted my perspective from configuring a server to evaluating it like an external assessor. Running Lynis, nmap, AppArmor checks and a service inventory required me to justify not only what I had configured but why it mattered and whether the evidence supported it. The before-and-after Lynis scores showed how changes such as SSH hardening and AppArmor enforcement produced measurable security improvements. The nmap scan reinforced the value of verification by proving that only port 22 was exposed, rather than assuming the firewall was correct. Reviewing running services also highlighted the importance of minimising the attack surface.

Most importantly, this week helped me develop an audit mindset—documenting configurations, validating them with tools and presenting findings clearly. This mirrors real system administration practice, where evidence, repeatability and justification are essential. By the end of the audit, I could not only secure an Ubuntu Server but assess its security posture and explain its remaining risks and overall readiness.

8. Conclusion

The final audit validates that the Ubuntu Server is securely configured, minimally exposed and supported by layered defence mechanisms including firewall restrictions, SSH hardening, AppArmor enforcement, automatic updates and intrusion prevention. The improvements measured by Lynis, combined with the external verification from nmap and service justification, show that each configuration decision across Weeks 1–6 contributed directly to a stronger security posture in Week 7. While some residual risks remain—primarily related to virtualisation constraints and the single-host design—they are acknowledged and manageable within the scope of the coursework. Overall, the system meets the Phase 7 requirements and demonstrates a clear, evidence-driven approach to secure server administration. The audit process has reinforced habits of verification, documentation and critical analysis that are essential for professional system management
